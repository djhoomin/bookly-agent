Bookly support agent01 / Thesis

Containment is the wrong north star.

The industry measures the share of tickets closed without a human. That pressure builds agents which confidently do the wrong thing rather than hand over, because an agent that refunds an out-of-window order closes the ticket and scores perfectly.

What I built toward instead

Resolution without harm.

The agent has to prove it knows enough to act before it acts. Two consequences run through every decision that follows: the rules live in code rather than in the prompt, and the clarifying question is a gate rather than a good habit.

The failure this prevents

A customer with two copies of Dune on one account, an ebook and a paperback. One is refundable, one is never refundable. An agent that guesses is right half the time, and the customer sees every miss.

Key decision03 / Policy is code

A prompt is a suggestion. A function is a rule.

A prompt saying "only refund within 30 days" is advisory. A model being helpful to an angry customer will find a reading of it that permits yes. This returns the same answer whether the customer is polite or furious, and it is testable.

age = (today - order.delivered_on).days
if age > RETURN_WINDOW_DAYS:
    return Decision(
        False, "outside_window",
        f"Delivered {age} days ago, outside "
        f"the {RETURN_WINDOW_DAYS}-day window.")

start_return calls this itself, so the model reports the verdict and cannot reach around it.

Every refusal has a code, not a mood

What I traded away

Flexibility. There is no path to a goodwill exception, which a real deployment needs. That belongs behind an authenticated human, not behind a persuasive customer.

Key decision04 / The gate

The clarifying question is a gate, not a behaviour.

start_return requires a resolved order_id. find_orders returns every match. When there is more than one, the model has nothing it can act on, so it asks.

Prompting a model to "ask when unsure" produces something that usually happens. Removing the code path produces something that always does.

On the ambiguous request the agent called exactly one tool and stopped. It had nothing to act on.

What I traded away

One turn of latency on ambiguous requests. Worth it: the alternative is a coin flip between refunding a returnable paperback and a non-returnable ebook.

Cases assert on outcomes, not wording. Did a refund fire, was a human brought in, was a state-changing action taken against the wrong order. Phrasing is not scored, because phrasing is not what goes wrong.

6 / 6against claude-opus-5, cold, no retries

The eval set ships with the agent rather than after it. An agent optimised for containment would fail four of these and score better on the metric most CX teams report.

What I would change first

Build the eval set from real transcripts. These six test failures I thought of, which is the weakest kind of test. One week of live traffic would produce the cases that actually matter, and they would not look like these. Retrieval, auth before state changes and a goodwill path are ordinary engineering. The eval set is what decides whether the agent improves or merely changes.
