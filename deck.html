Bookly support agent01 / Thesis

Containment is the wrong north star.

The industry measures tickets closed without a human. That pressure builds agents which confidently do the wrong thing rather than hand over: an out-of-window refund closes the ticket and scores perfectly.

What I built toward instead

Resolution without harm, at a price that scales.

The agent proves it knows enough to act before it acts, and the expensive model is asked only for the turns that need one. Three decisions follow, each enforced in code rather than requested in a prompt.

The failure this prevents

Two copies of Dune on one account, an ebook and a paperback. One is refundable, one never is. Guessing is right half the time, and the customer sees every miss.

The shape is not new

Banking and insurance have run automated decisions for decades on one rule: where risk is low the system decides alone, and where uncertainty passes what the business will tolerate, a person makes the final call.

risk score         -> triage.py
rules engine       -> policy.py
manual review queue -> escalate_to_human
case ownership     -> after handover, no model call

Buyers remember the dealership chatbot that sold a Tahoe for a dollar and the airline held liable for a bereavement fare its chatbot invented. Both were a model extending itself under pressure.

The gate, which is structural rather than instructed 
start_return(order_id, reason)
    ^ required, never inferred

find_orders(email) -> every match

  2 matches -> nothing to act on
            -> the model must ask

Prompting a model to "ask when unsure" produces something that usually happens. Removing the code path produces something that always does. The system prompt holds tone and judgement only, under 250 words with no eligibility rule in it, and that absence is the evidence: everything enforceable moved into code.

Account data needs a verified email: a code to the inbox, checked by a tool, and the model never sees the code. An order number is not access. Once a person owns the conversation, the agent makes no further model call. Nothing left to push.

Key decision03 / Policy is code

Don't prompt what should have been code.

A prompt saying "only refund within 30 days" is advisory, and a model being helpful to an angry customer will find a reading of it that permits yes. Deterministic is almost always preferable: this returns the same answer whether the customer is polite or furious, and it is testable.

age = (today - order.delivered_on).days
if age > RETURN_WINDOW_DAYS:
    return Decision(
        False, "outside_window",
        f"Delivered {age} days ago, outside "
        f"the {RETURN_WINDOW_DAYS}-day window.")

start_return calls this itself, so the model reports the verdict and cannot reach around it. How the code gets written does not matter, typed or generated from a procedure a CX team wrote in plain language. What matters is that at decision time the rule runs; the model does not interpret it.

General questions have no verdict, the answer is the prose, so a second model reads every such reply against the published text. "Usually 2 days" where the text says 3 to 7 gets replaced with the text and an offer of a person. Same rule, applied to words: the model may explain the policy and may not extend it.

What I traded away

Flexibility. There is no path to a goodwill exception, which a real deployment needs. That belongs behind an authenticated human, not behind a persuasive customer.

Key decision04 / Two cheap calls before the expensive one

Opus to read a database row is not a business.

Two cheap passes before the expensive model sees a turn. Haiku 4.5 picks the tier. Mistral's moderation model, which is free, decides abuse and self-harm. Haiku keeps the fraud signals a general moderator has no name for.

Measured from 213 real API calls across the eval suite, at list prices. Twenty of twenty-three conversations never touched Opus: the three that did were the fraud signal, the threat and a planted instruction, because risk routes heavy. An abusive customer costs more, and the trace shows it.

Swap the model and the destinations hold. The same suite on DeepSeek V4.1 Flash through OpenRouter, both tiers: 20 of 20 cases, 40 of 40 phrasings on rerun, every return decision through policy.py, $0.0012 a conversation. The model decides how to reach the decision. The code decides what the decision can be.

Why a misrouted turn is survivable 
"I'd like to return my Dune"

  triage -> simple  -> haiku-4-5
  find_orders -> 2 matches
  agent asks which one          OK

The classifier called that simple and it is arguably complex. It did not matter. Correctness lives in the gate and the policy function, and both are model-independent, so routing is an optimisation, not a safety mechanism. A triage miss costs a less polished reply, never a wrong refund.

And the second job

Two screeners. Mistral's moderation model decides abuse: a threat scores 0.65 violence_and_threats, is logged, and the eligible refund still goes through, because tone is not policy. Haiku keeps what no general moderation model knows: claimed authority to override policy is fraud_signal, routed to Opus, refused anyway. Both land in abuse_log.jsonl with the message attached.

What the trace caught during the build

Four of eight turns were refusing customers without calling the policy function, deciding from the published prose instead. The gate sealed wrong approvals and left wrong refusals open. Fixed by adding a read-only check_return_eligibility, so there is an authoritative answer without attempting the action. Every refund decision now records a code, two previously invisible refusal reasons appeared, and it came out 24% cheaper.

What I would change first, given a production context

Build the eval set from real transcripts. The 23 cases are the beers the QA engineer orders. The two holes that would have cost money or embarrassed a customer, a refund on "never received" and a true delivery date replaced as invented, were found by a person typing at the UI while every case was green, and became cases afterwards. Invented cases only contain what you already thought of. Then real identity, since a code proves an inbox and a session proves a customer, and a goodwill path behind a human.
